# Развёртывание на своём сервере

Приложение больше ничем не привязано к Vercel: в коде нет ни одной ссылки на
его переменные, шрифты лежат в репозитории, ссылка шеринга строится из адреса
страницы. Всё, что раньше молча делала платформа, теперь описано здесь.

## Быстрый старт

```bash
export NEXT_PUBLIC_SITE_ORIGIN=https://taro.tutu.ru
export TUTU_MCP_URL=https://mcp.tutu.ru/mcp
docker compose up -d --build
```

Проверка, что живо: `curl http://localhost/healthz` → `{"status":"ok",…}`.

## Что нужно от эксплуатации

| Что | Зачем | Значение |
|---|---|---|
| Домен и TLS-сертификат | Мессенджеры не разворачивают превью с http | напр. `taro.tutu.ru` |
| Порт 80 (и 443 после TLS) | Точка входа nginx | — |
| Исходящий доступ к `mcp.tutu.ru` | Без него нет ни билетов, ни отелей | HTTPS |
| Исходящий доступ к ИИ-шлюзу | Необязателен, см. ниже | HTTPS |
| Ядра | По одной реплике на ядро, минус одно на nginx и систему | 2–4 |
| Память | ~250 МБ на реплику под пиковой нагрузкой | 1–2 ГБ |
| Диск | Образ 307 МБ + до 1 ГБ под кэш картинок | 5 ГБ |

## Переменные окружения

**`NEXT_PUBLIC_SITE_ORIGIN` — единственная обязательная, и она читается во
время сборки, а не запуска.** Next вшивает её в бандл и через неё вычисляет
`metadataBase`. Если её не задать, Next подставит `http://localhost:3000` —
сборка не упадёт, приложение будет работать, но в мета-тегах каждого расклада
окажется адрес localhost, и **шеринг перестанет разворачиваться в картинку во
всех мессенджерах**. Симптома в логах не будет.

Поэтому в `docker-compose.yml` она передана как `build.args`, а не в
`environment`. Меняете домен — пересобираете образ, а не перезапускаете
контейнер.

Остальные:

- `TUTU_MCP_URL` — по умолчанию `https://mcp.tutu.ru/mcp`.
- `AI_BASE_URL`, `AI_API_KEY`, `AI_MODEL`, `AI_AUTH_HEADER`, `AI_AUTH_PREFIX`,
  `OPENAI_API_KEY` — все необязательные. Без них оракул говорит написанными
  вручную текстами: это поддерживаемый режим, а не поломка. Полный контракт —
  в `.env.example` и разделе «Тексты от ИИ» в README.
- `APP_REPLICAS` — сколько процессов приложения поднять, по умолчанию 3.

Ключ ИИ на сервере кладите в файл окружения с правами `600`, а не в
`docker-compose.yml`: последний лежит в репозитории.

## Почему именно так

### Реплики вместо одного процесса

Node однопоточный, и это первое, за что обычно тревожатся при переезде. Для
этого приложения тревога почти беспредметна: его работа — это ожидание ответа
Туту (бюджет поиска 18 секунд), а ожидание событийный цикл держит тысячами.
Поток занят, только когда что-то считает.

Считает здесь ровно одно место — Satori, который рисует картинки для шеринга.
Вот из-за него и нужны реплики: они кладут эту работу на разные ядра. Заодно
падение одного процесса перестаёт быть падением сервиса — чего `cluster` в
одном процессе не даёт.

Ставьте `APP_REPLICAS` по числу ядер минус одно.

### Буферизация снята только на странице расклада

Страница `/r/<код>` отдаётся в два приёма: карты уходят браузеру сразу, дорога
дописывается, когда ответит Туту. Nginx по умолчанию буферизует ответ и отдал
бы всё одним куском через 18 секунд — двухфазный ритуал превратился бы в одно
долгое пустое ожидание.

Но выключать буферизацию глобально нельзя: **nginx не умеет кэшировать то, что
не буферизует**, и картинки шеринга перестают кэшироваться. Ровно эта ошибка и
была допущена в первой версии конфига; единственный её симптом —
`X-Cache-Status: MISS` на третий одинаковый запрос. Поэтому буферизация снята
в одном `location`, и приложение шлёт `X-Accel-Buffering: no` только на том же
маршруте.

Если будете переписывать `deploy/nginx.conf` — это то, что нельзя потерять.

### Картинки кэшируются в nginx

`opengraph-image` и `thumb` — чистые функции от кода в ссылке: один и тот же
адрес не может дать разную картинку. Раньше их кэшировал CDN Vercel, теперь
это делает nginx (`proxy_cache`, 30 дней, `proxy_cache_lock` — чтобы пятьдесят
одновременных разворачиваний одной ссылки стоили одного рендера, а не
пятидесяти).

Сами расклады не кэшируются никогда и не должны: пророчество заморожено в
ссылке, а цены обязаны быть свежими при каждом открытии.

### `proxy_read_timeout 60s`

Должен с запасом превышать бюджет поиска (18 секунд) плюс время ответа ИИ.
Стандартные 60 секунд подходят; если будете уменьшать — не ниже 40, иначе
nginx оборвёт соединение, пока оракул ещё говорит.

## Обновление

```bash
git pull
docker compose up -d --build
```

`stop_grace_period: 25s` даёт текущим запросам доехать: в полёте может быть
чужой поиск, который человек прямо сейчас ждёт на экране.

Конфиг nginx смонтирован томом и **не перечитывается при `up --build`** — после
его правки нужен `docker compose restart nginx`.

## Диагностика

```bash
docker compose ps                          # кто жив
curl -s localhost/healthz                  # ответит — и скажет, какая реплика
docker compose logs -f app                 # логи приложения
curl -sI localhost/r/<код>/opengraph-image | grep -i x-cache-status
```

`X-Cache-Status` должен стать `HIT` со второго запроса. Если остаётся `MISS` —
скорее всего где-то вернули буферизацию, см. выше.

Живой смоук против настоящего Туту (без браузера) — `npm run smoke`, описан в
README.

## Чего здесь намеренно нет

- **Кэша, общего между репликами.** `unstable_cache` в `narrator.ts` держит
  тексты ИИ в памяти процесса, поэтому каждая реплика греет свой. Для текстов
  это безобидно: промах стоит одного обращения к шлюзу. Если реплик станет
  много и это начнёт быть заметно по счетам за ИИ — понадобится общий
  cache handler (Redis), см. «Shared cache» в документации Next по
  самохостингу.
- **CI, который гоняет тесты.** Как и на Vercel, проверки запускаются руками:
  `npm run lint`, `npx tsc --noEmit`, `npm run test`, `npm run build`,
  `npm run test:e2e`. См. раздел «CI/CD» в README.
- **TLS.** Compose поднимает только HTTP на 80. Сертификат ставьте либо
  внешним балансировщиком Туту, либо добавьте `certbot` рядом с nginx —
  зависит от того, как это принято в вашей инфраструктуре.
